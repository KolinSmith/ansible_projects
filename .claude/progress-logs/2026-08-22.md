### Uptime Kuma "forgejo-runner disk" Monitor — Fixed (2 months broken)

**Discovery**: Monitor `forgejo-runner disk` (push monitor, token `oCTYwPZKEB`) showing red in Uptime Kuma.

**Investigation**: Queried `uptime-kuma`'s sqlite db directly on `dmz` (`/app/data/kuma.db`, `monitor`/`heartbeat` tables). Found the monitor has **never once received a successful heartbeat since it was created on 2026-06-23** (see that day's log — this is the same disk-heartbeat cron added during the Forgejo CI runner recovery work) — 1,417 consecutive "down"/"no heartbeat" records, zero "up".

**Root cause**: Unescaped `%` in the crontab command. Cron treats an unescaped `%` as a newline (splitting the command, feeding the remainder to the command's stdin) — confirmed via `journalctl -u cron`, which showed the executed command truncated exactly at the first `%`:
```
CRON[61842]: (root) CMD (USED=$(df / --output=pcent | tail -1 | tr -d " )
```
The original cron line has `%` in both `tr -d " %"` and `msg=disk%20...`. A manual run of the same command from an interactive shell "worked" (which is why this went unnoticed) since `%` isn't special outside of cron.

**Fix**: Escaped both `%` as `\%` in root's crontab on `forgejo-runner` (192.168.9.101). Verified by simulating cron's own unescaping (`sed 's/\\%/%/g'`) and running the resulting command directly — confirmed it correctly posts to the Kuma push URL and registers an "up" heartbeat (`disk 35pct`). Backup of the original crontab left at `/tmp/crontab.bak` on the host.

**Also incidentally fixed**: SSH to `forgejo-runner` was failing with "Host key verification failed" — turned out to be `StrictHostKeyChecking=ask` + non-interactive session (not a real key-change warning, no "REMOTE HOST IDENTIFICATION HAS CHANGED" banner). Verified the presented key via independent `ssh-keyscan`, matched, added to `known_hosts`.

**Not done**: no code/PR needed for this — the fix is a live crontab edit on the host, not something tracked in this repo (the cron was never added via Ansible, just installed by hand back on 2026-06-23 per that day's log). Worth considering whether it should be moved into an Ansible role so it's not a hand-edited snowflake, but not done today.
